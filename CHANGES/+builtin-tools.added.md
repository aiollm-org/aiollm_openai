Built-in tools of the shared request: `WebSearch` (with `allowed_domains` and `user_location`) and `CodeExecution` go in `tools=` beside the functions and reach OpenAI as `web_search` and `code_interpreter` (in an `auto` container); a `ProviderTool` of this provider is sent as its own definition, and a tool OpenAI does not run raises `RequestValidationError`. The new `aiollm_openai.tools` module builds those provider tools for the rest: `web_search` (`search_context_size`, `external_web_access`, the dated type), `file_search` and `code_interpreter` (a container to reuse, or the files and memory of a new one). The calls OpenAI ran come back as `server_tool_calls` (`web_search_call`, `file_search_call`, `code_interpreter_call`, `image_generation_call` and `mcp_call` items; `COMPLETED`, `FAILED` with the item's error, `INCOMPLETE`) and the annotations of the text as `citations` (`url_citation` a `URL`, `file_citation` a `FILE`, `container_file_citation` a `CONTAINER_FILE`, their spans moved to the joined text), in a response and in the `CompletedEvent` of a stream, where each call is also a `ServerToolCallEvent` when its item is added and when it is done. An `assistant` turn of `to_turn()` with OpenAI's own output goes back as those output items, so the search calls and reasoning items reach the next request.
